# 小组件解锁刷新与保活

## 使用

1. 安装后打开应用，将需要的小组件添加到桌面。
2. 在“我的 / 设置 → 课程提醒设置 → 小组件解锁刷新与保活”开启前台保活，允许通知权限。通知中可停止保活。
3. 可选：允许悬浮窗权限后，返回页面再次开启透明悬浮窗保活。悬浮窗大小为 1 像素，背景透明，不接收触摸和焦点；系统可能显示悬浮窗提示。
4. 可选：安装并启动 [Shizuku](https://shizuku.rikka.app/download/)，返回此页面请求授权，再点击“通过 Shizuku 允许后台运行”。此操作只影响本应用的设备空闲白名单和后台运行 AppOps，应用前保存原策略，并在写入后读取核对。可点击“恢复原来的后台策略”撤销；失败时保留原策略备份以供重试。Android 8 仅设置其支持的后台运行项。
5. 按手机系统要求允许自启动、后台运行，并设置电池优化豁免。页面分别显示实际前台服务、悬浮窗和 Shizuku 授权状态。

保活默认关闭。解锁监听使用 Application 动态注册的 `ACTION_USER_PRESENT`，不依赖页面停留在前台；无桌面小组件时不创建解锁刷新任务。全部四种小组件共用刷新入口，连续解锁会合并未完成的任务。刷新 Worker 等待渲染完成后才结束。

保留每 15 分钟的 WorkManager 定期刷新及每日数据同步。移除某一种小组件时，只要仍存在其他类型的小组件，就保留后台刷新任务。

## 系统限制

- 前台服务与透明悬浮窗可提高后台存活概率，不能保证永远不被结束。WorkManager 也受系统调度影响，刷新可能延迟。
- 被“强行停止”后需手动重新打开应用。强行停止会阻止应用接收解锁及开机广播。
- 手机重启或应用升级后，若之前开启前台保活，会尝试恢复服务；若系统禁止启动，需打开应用恢复。非 root 的 Shizuku 通常需在手机重启后重新启动。
- 关闭前台保活会移除悬浮窗，但不会自动撤销已应用的 Shizuku 策略；需单独点击恢复。恢复策略需要 Shizuku 处于启动并授权状态。
- 后台策略备份和保活选项不随系统备份迁移到其他设备。

## 构建与手机验证

构建环境需要 JDK 21 和 Android SDK（由项目 Gradle 配置指定版本）：

```sh
./gradlew :androidApp:assembleDebug
```

安装对应手机架构的 APK 后，在真实手机验证以下行为：

1. 添加四种小组件，开启保活，回到桌面，锁屏后正常解锁。检查日志 `WidgetUiUpdateWorker 开始执行` 与四种规格的刷新记录，并核对显示时间、今日剩余课程和跨日课程。
2. 连续锁屏与解锁，确认没有重复刷新任务堆积；仅亮屏但未解锁时，不应触发解锁刷新。
3. 删除一种小组件，其余小组件仍能解锁刷新；删除所有小组件后，解锁不应产生刷新任务。
4. 检查前台保活与悬浮窗的独立开关、通知权限拒绝、悬浮窗权限拒绝，以及通知中“停止保活”后的资源释放。
5. 分别验证 Shizuku 未启动、拒绝授权、授权成功、连接中断，以及应用和恢复策略。恢复后应与首次应用前记录的三项策略一致。
6. 重启手机、应用升级、系统后台清理与强行停止后，按上述限制核对恢复行为。
